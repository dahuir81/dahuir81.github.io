漏洞档案

CVE-2026-109618 CVSS v4.0 · 9.2 Critical

RCE via OOM corruption（内存耗尽导致的损坏）

根因：当一个请求耗尽 PHP 的每请求内存上限时，PHP 会通过"直接跳出当前执行"的方式中断它。在若干处代码中，此刻请求内存只初始化了一半，中断让这部分数据停留在坏状态；请求结束时的清理代码随后把这份无效数据当成有效数据来处理。

攻击方式：攻击者可以用精心构造的 文件上传（multipart）请求主动制造内存耗尽——例如一个 part 携带海量 header，或者塞入大量空文件字段——而请求体积始终控制在服务器允许范围内。内存耗尽后，清理阶段就会被导向可利用的路径。

为什么危险：这是"先于应用代码触发"的漏洞。攻击请求不需要命中任何 PHP 脚本业务逻辑。

GHSA-w8hw-w9fx-j79wCWE-内存处理

CVE-2026-109619 CVSS v4.0 · 9.2 Critical

RCE via stale global state（残留全局状态）

根因：请求持有的内部状态在背后的内存被释放之后仍然残留。同一个 worker 处理下一个请求时，可能在正常初始化重置之前就用到这份过期状态——典型的跨请求污染。

攻击方式：已确认的路径包括 session.upload_progress 机制，以及 PHP 8.5 的致命错误回溯（fatal error backtrace）。攻击者先构造一个请求把状态"做脏"，再由后续请求踩中。

为什么阴险：跨请求的状态泄漏意味着攻击可能分多步完成，单个请求看起来完全正常，日志审计容易漏掉。

✅ 升级后必须确认一件事

升级完 一定要重启所有 worker（php-fpm / httpd / 容器实例），否则旧的进程带着旧二进制继续跑，补丁等于没打。用 php -v 和 php-fpm -v 分别确认版本号。

暂时升不了？这是官方给的应急缓解

必须先说清楚：以下措施只能减少部分攻击路径，不能让系统变安全。官方原话如此，别把它们当解决方案。

针对 CVE-2026-109618（OOM 路径）

  • 设置 memory_limit=-1，用 php_admin_value（FPM pool 或 Apache 配置）这种应用改不了的方式设置，并逐一检查没有 pool / 目录 / 应用配置把有限制的值改回来。注意：这消除了"可控的内存上限失败"，但底层分配失败仍可能走到漏洞路径。
  • 压低 post_max_size：不需要上传的场景设 8M；有上传需求设 32M，并保证 upload_max_filesize 小于它。
  • 在 Web 服务器 / 反向代理层限流：解码后请求体大小、输入字段数、multipart part 数、header 数量、嵌套深度，全部设上限。这些限制必须覆盖没有可用 Content-Length 的请求。
  • 用容器或 cgroup 做可用性边界，策略上只杀受影响的 worker。不要改用 RLIMIT_AS / RLIMIT_DATA 限制内存——反而可能触发漏洞。

针对 CVE-2026-109619（状态残留路径）

  • 设置 session.upload_progress.enabled=0，然后重启所有 worker。写在 php.ini 或 FPM pool / 服务器配置里，不能靠 ini_set() 或 FPM 的 .user.ini。
  • PHP 8.5 额外设 fatal_error_backtraces=0，同样要重启所有 worker。
  • 移除每请求生效的无效或废弃配置项——它们在初始化之前就会产生诊断输出。用 error_reporting、display_errors 或 @ 掩盖诊断信息没用。
  • 修掉攻击者可触发的致命错误和执行超时，包括回调、上传/导入处理、清理阶段的失败。

关键：这个漏洞在 PHP 里藏了 14 年

OpenAI 联合创始人格雷格·布罗克曼在发帖中提到，这个 bug 在 PHP 中已存在 14 年。Futurism 的报道更具体：漏洞存在于可追溯到 2004 年的 PHP 版本中。

Calif 团队的原话是：他们本来「没指望能找到什么严重的东西」，因为 PHP 被安全社区翻来覆去审计了这么多年。

为什么这件事的性质和以往不同

Wiz 的原话，值得逐字读

「有了前沿 AI 模型和合适的工具，单个研究员用一周完成了以前需要世界级团队数月才能完成的工作。」

他们还表示：底层缺陷已经存在了几十年，但要证明它可被利用，需要一条「人类研究员实际操作上几乎做不到」的攻击链。

这句话的分量在于：过去我们评估一个老漏洞的风险时，默认是「十几年没人利用，说明利用门槛很高」。AI 直接把这条经验按性价比重算了。

Wiz 把它和 Heartbleed、Log4Shell 并列

Wiz 自己的类比逻辑是：

  • 2014 年 Heartbleed —— 暴露了「共享基础设施」的脆弱性
  • 2021 年 Log4Shell —— 暴露了「深层依赖」造成的面状暴露，组织连资产都数不清
  • 2026 年 PHP2Shell —— 暴露了「AI 改变了老 bug 的实际可利用性」

Wiz 的结论是：这可能是 AI 时代的转折点——古老代码一直都在，AI 改变的是「理解弱点并转化成可用 exploit」的能力。

对后续网络安全的影响（本文重点）

1. 防御窗口被压缩：从「月」到「天」

微软 2026 数字防御报告给出的对照数字很刺眼：攻击时间线在压缩，但企业修复一个严重的外部暴露漏洞，仍然需要 30 到 60 天。

这个错配意味着：系统在被利用之后很久，仍然处于可利用状态。Google 威胁情报组 2026-09-30 的报告与微软的结论一致。

这次事件的现实版注脚：NSA 在社交媒体上直接督促组织升级 PHP，升不了就下线；路透社报道欧洲有政府网站真的下线了。

2. 漏洞发现量的量级变化（不是线性增长）

来源数据
红帽产品安全团队2025 全年分诊 7,722 个漏洞；2026 年前四个月 2,826 个；2026-05-01 至 05-15 半个月暴增 712 个，按此推全年将破 17,000，是 2025 年的两倍多
Mozilla × Anthropic 合作JS 引擎中先发现 22 个，随后整库扫描又识别出 271 个
Mythos 系 AI 工具截至 2026 年 5 月中，两周内标记 10,000+ 个潜在问题——相当于传统方式一整年的发现量

这条曲线的意义：AI 时代不是「漏洞变多了」，是「原本就存在但没人看见的漏洞，现在被批量看见了」。

3. 攻防重心前移：从「发布后竞速」到「合并前拦截」

过去的攻防竞争发生在软件 release 之后：攻击者、研究员、防御方围绕已发布的软件抢时间。

现在趋势明确前移：谁能在代码合并前发现问题，谁就能省掉后面整条披露、修复、应急的成本链。安全正在变成软件生产线里的质量控制环节，而不是发布后的补丁工作。

对企业最直接的含义：SBOM、依赖清单、互联网暴露面清单，这几样从「合规动作」变成「应急前提」。补丁出来那天，你数不清自己有几套 PHP，就等于没法应急。

4. 维护者成了新瓶颈——这是最被低估的风险

⚠️ AI 挖漏洞的副作用：真实的漏洞报告和噪音一起涌向开源维护者

当 AI 能批量产出「看起来合理」的漏洞报告，而开源维护者手里只有有限的时间和人力，结果就是分诊能力被淹没。真正的高危报告可能排在几百条低质量报告后面。

这也是 OpenAI 的「Patch the Planet」为什么配了 Trail of Bits 的工程师人工复核每一条 AI 发现，才送到维护者手上——他们的判断是：维护者的时间是瓶颈，不是发现能力。

5. 声誉风险：老代码的「安全假设」集体失效

以前判断一个库安不安全，常有一条经验：「它被人审了很多年」。PHP 藏了 14 年的洞、Linux 内核 NFS 驱动从 2003 年就在的堆溢出（Anthropic 的 Nicholas Carlini 用 Claude Code 挖出）——这些都指向同一个结论：

「被审了很多年」不再是安全信号。它只说明「人类审计的性价比到顶了」。而 AI 把审计的性价比重新拉起来，于是所有老项目都要按新标准重估一遍。

6. 攻击面转移：当洞更难挖，攻击者会去改入口

这是一个反向推演，但逻辑很硬：如果头部项目持续被 AI agent 扫描，低垂和中等难度的漏洞逐渐被扫干净，那么纯粹挖 0day 的成本会重新上升。

那时候攻击者的理性选择是：不找已有漏洞，而是让未来版本主动带入可利用的问题——投毒、供应链操纵、更易被接受的 PR、更隐蔽的代码改动。AI 会同时压低这条路线的成本。

7. 「AI 主动帮人找漏洞」的边界之争，还没定论

Calif 拿到 GPT-5.6 Sol 的授权去挖 PHP，OpenAI 事后自己复核发现了更多细节，白宫把这事定性成「美国超级智能增强国家安全」的证据——这个话题在英文安全圈吵得很凶：

  • 支持方：同样的能力在防御方手里，就是国家能力的延伸
  • 质疑方：挖漏洞的能力是双向的，今天能批量找到并负责任披露，明天同样的模型也能被用来批量找未修补的目标

目前没有定论。但可以确定的是：这类辩论不会再停留在理论层面，因为 PHP2Shell 已经是既成事实了。

落到我们自己的行动清单

  1. 立刻把所有 PHP 升到 8.5.12 / 8.4.27 / 8.3.36 / 8.2.35，并重启所有 worker
  2. 盘一遍互联网暴露面：到底有多少套 PHP、多少个版本、谁负责。这次数不清，下次还是数不清
  3. 建立「应急通道」：能绕过常规变更窗口紧急发版的能力。30-60 天的修复周期在 AI 时代是致命短板
  4. 把安全扫描塞进 CI/CD，别等发布后再扫。攻防重心已经前移了
  5. 对依赖做持续评估，别信「这个库审了很多年」这种论证。AI 随时可能推翻它
  6. PHP 8.2 用户：12 月 31 日 EOL，打完补丁就得排迁移，别拖

一个行业视角的判断

这不是"应用写错了"，是"语言运行时自己裂了"。两个漏洞都发生在请求生命周期的收尾阶段——清理和状态重置。这类 bug 的共性在于：一旦被触发，攻击者已经在 PHP 解释器内部拿到了执行权，应用层的 WAF、参数校验、鉴权中间件全部失效。

所以 mod_php 风险最高不是偶然：它把 PHP 直接嵌在 Apache 进程里，请求在进入任何应用代码前就要走完 PHP 的解析和清理流程。换成 PHP-FPM 会好一些，但也只是把攻击面从"进程内"挪到"worker 内"。

长期启示：运行时级别的漏洞只能靠"快速升级能力"来兜底。你的升级链路如果是"等运维排期"或"走 remi 源"，这次就是一次压力测试——测出来的都是真问题。
